## Scope
Final check before tagging (user 2026-11-03): can the device handle a large dashboard?
- Stress config (committed as tools/testdata/stress/config.yaml, no secrets): the maximum number of tabs (16) with full grids
  in both orientations, every widget type incl. new ones (notifications, weather forecast, media, groups, covers, climate,
  history graphs of every type, several graphs per tab), long names, many entities (the user's real ids reused + some
  nonexistent ids for `n/a`). Generated by a small script so sizes can be scaled.
- Back up the user's config.yaml from the SD card first (config.yaml has no secrets; never touch secrets.yaml), upload the
  stress config with the existing USB file protocol, restore the original at the end and verify it is back.
- Measure (serial + camera): config parse + cache time, heap free/min, largest free block, PSRAM use, loop_stack_free, state
  fetch size and time (template response), render time per tab, tab change time, tap timing (queue_wait_ms,
  call_to_response_ms), history fetch batch time, sleep/wake (rocker wake by the user only, else scheduled wake with a short
  interval), no crash / TASK_WDT / stack canary / OOM over >= 15 min of tab cycling + taps.
- Find the limits: if something breaks, shrink until it works and record the limit; fix crashes, or enforce a documented
  limit with a clear config error instead of crashing.

## Acceptance criteria
- [x] Report with the numbers above at max size; any limit found is enforced and documented in docs/guide/09-config-reference.md.
- [x] No crash in 15 min; user's config restored (diff equal).
